# Рабочий процесс

PLAN → ISSUE → BRANCH → WORK → TEST → PR → REVIEW → MERGE

1. **PLAN** — определить задачу, границы и критерии готовности.
2. **ISSUE** — оформить задачу в GitHub с ответственным и проверками.
3. **BRANCH** — создать ветку `rig/<task>`, `kai/<task>`, `nova/<task>` или `orbit/<task>`.
4. **WORK** — выполнить изменения в своей рабочей зоне.
5. **TEST** — выполнить необходимые проверки и записать результаты.
6. **PR** — открыть pull request с описанием результата и проверок.
7. **REVIEW** — проверить изменения, границы задачи и отсутствие секретов.
8. **MERGE** — перенести проверенные изменения в `main` после review.

`main` — только проверенное состояние. Force push и переписывание истории `main` без прямой команды оператора запрещены.

Перед commit проверить `git status`, состав изменений и `git diff --stat`. Для новых файлов дополнительно проверить их содержимое: обычный `git diff` не показывает untracked-файлы. После staging проверить `git diff --cached --stat` и staged-содержимое на секреты.

Первичная инициализация репозитория в `main` выполняется по прямой команде оператора; дальнейшая работа следует процессу выше.

## Облачная координация и интеграция

ORBIT — CLOUD / INTEGRATION: проверяет состояние общего репозитория, координирует Issues/PR и CI/CD, сверяет результаты RIG — SYSTEM, KAI — FIELD и NOVA — TOOLING. Перед интеграцией проверяет diff, границы задачи, секреты и фактические результаты проверок. Публикация ветки и создание PR не означают merge; интеграция в main выполняется после review и разрешения оператора.
