# RED └•TEAM•┐ HQ

Статус: проект спецификации для review оператора. Область: архитектура взаимодействия команды; программная реализация, сервисы и автоматизация не входят в этот документ.

Термины MUST / MUST NOT означают обязательное правило / запрет; SHOULD — рекомендацию, отступление от которой требует записанного обоснования. Утверждение этой спецификации не подтверждает внедрение описанных механизмов.

Источники: [TEAM](../TEAM.md), [AGENTS](../AGENTS.md), [WORKFLOW](../WORKFLOW.md), [SECURITY](../SECURITY.md), [NODE](NODE.md). HQ дополняет инженерный workflow и не расширяет полномочия участников. Изменения ролей и разрешения на интеграцию остаются за оператором. Конфликт инструкций MUST быть зарегистрирован как BLOCKER до затронутой реализации.

## 1. Цель HQ

RED └•TEAM•┐ HQ — единый командный центр: протокол назначения задач, независимого исследования, обмена доказательствами, инженерного обсуждения, принятия решений и контроля интеграции.

HQ связывает распределённые рабочие среды через общий контракт задачи и проверяемые записи. Он решает проблемы рассинхронизации требований, преждевременного согласия, потери аргументов, дублирования работы и интеграции непроверенных изменений.

Единица работы — mission с идентификатором, оператором, координатором, ответственными инженерами, границами, критериями приёмки и текущей фазой. GitHub Issue SHOULD служить публичной записью mission, PR — записью изменения. Секреты и непубличные исследования MUST NOT попадать в публичный репозиторий.

HQ задаёт поведение команды, а не отдельную личность. Один запущенный агент MUST NOT изображать исследования, сообщения или согласие других инженеров.

## 2. Участники

Ограничения: решение оператора MUST быть записано; расширение scope возвращает затронутые этапы на пересмотр. Operator MUST NOT выдавать отсутствие проверки за успех или закрывать технический BLOCKER одним указанием продолжать. Если риск принимается организационно, это требует изменения scope и явной фиксации остаточного риска, а не объявления проблемы исправленной.

Не может: исследовать, голосовать, спорить, закрывать BLOCKER, утверждать решение, выполнять реализацию, review или merge. NODE не пятый инженер и не человек-сотрудник. Идентичность сохраняется согласно [NODE.md](NODE.md).

## 3. Жизненный цикл задачи

Получение задачи → Разбиение → Независимое исследование → Обмен выводами (SYNC) → Инженерная дискуссия → Поиск лучшего решения → Проверка проекта решения → Реализация → Проверка результата → Merge → Mission Report.

| Фаза | Обязательная запись и условие перехода |
| --- | --- |
| Получение задачи | Mission ID, цель оператора, scope/non-goals, критерии приёмки и доступные полномочия |
| Разбиение | Подзадачи, интерфейсы, зависимости, участники, ответственные и общий набор исходных фактов |
| Независимое исследование | Отдельный зафиксированный пакет каждого назначенного инженера; чужие пакеты недоступны |
| SYNC | Одновременное раскрытие пакетов, список полученных и отсутствующих материалов |
| Engineering Debate | Аргументы, альтернативы, риски, разногласия и BLOCKER с владельцами |
| Поиск лучшего решения | Сравнение вариантов по критериям, выбранная версия проекта, consensus |
| Проверка проекта решения | Выполнимость, совместимость, зависимости, план проверки/отката; BLOCKER отсутствуют |
| Реализация | Изменения только согласованного scope и версии решения в рабочих ветках |
| Проверка результата | Доказательства на точном commit, review, явные failed/skipped/unrun результаты |
| Merge | Явное разрешение оператора, актуальные проверки, отсутствие BLOCKER; интеграция через PR |
| Mission Report | Состояние интеграции, результаты, ограничения, остаточные риски и последующие задачи |

Проверка до реализации проверяет проект решения и существующие предпосылки; она не доказывает работоспособность ещё не написанного кода. Внешние эксперименты допустимы только в отдельно разрешённом scope; эта спецификация не требует писать код для исследования.

Изменение требований, новая существенная находка или неудачная проверка MUST вернуть затронутую часть на соответствующую фазу. Ветка и разрешение на записи не отменяют фазовые ограничения. Если merge заблокирован или запрещён, mission остаётся READY FOR REVIEW / WAITING; промежуточный отчёт не объявляется завершением интеграции.

## 4. Независимое исследование

Каждый назначенный инженер MUST сначала работать самостоятельно с одинаковым исходным контрактом mission. До SYNC никто из инженеров не видит исследования остальных. Общие исходные материалы допускаются; чужие выводы, планы и промежуточные результаты — нет.

Каждый пакет MUST содержать автора, mission ID, версию требований, рассмотренные варианты, факты и ссылки, метод проверки, результаты, предположения, ограничения, риски и рекомендуемое решение. Факты MUST быть отделены от гипотез.

Копирование чужих выводов и выдача их за независимое исследование запрещены. До SYNC пакеты MUST храниться в изолированных каналах/областях, недоступных остальным участникам исследования. Публичная ветка или общий чат такой изоляции не обеспечивают. Конкретный механизм изоляции пока не реализован; если доступ разграничить нельзя, координатор MUST объявить BLOCKER, а не заявлять независимость.

До раскрытия фиксируется версия каждого пакета и время завершения. Если инженер увидел чужие выводы раньше, это MUST быть раскрыто; его материал не считается независимым. Оператор определяет пересмотр процедуры без имитации повторной независимости.

## 5. SYNC

SYNC начинается после фиксации всех назначенных пакетов. Координатор публикует их совместно в общем разрешённом канале. Пропуск участника требует явного решения оператора об изменении состава mission; молчание не означает сдачу исследования.

Публикуются исходные версии, авторство, факты, методы, варианты, риски, неизвестные и рекомендации. Запрещены секреты, скрытое редактирование первоначальных выводов, выборочное сокрытие возражений и подмена отсутствующего исследования пересказом координатора.

Реестр SYNC MUST связывать mission, авторов, версии пакетов и общую версию требований. Исправления публикуются как новая версия с причиной; первоначальная запись сохраняется. Общая сводка MUST различать совпадения, противоречия и пробелы, а не превращать их в преждевременное согласие.

## 6. Engineering Debate

Engineering Debate — обязательный центральный этап HQ. Его предмет — решения и доказательства, а не личности, статус или убедительность речи.

Каждый назначенный инженер MUST проверить предложения, критиковать выявленные недостатки, искать риски, рассмотреть альтернативы, аргументировать позицию и не соглашаться без проверки. Если обоснованных возражений нет, он фиксирует, что именно проверено и почему альтернативы хуже; придумывать спор для выполнения процедуры запрещено.

Аргумент MUST включать: обсуждаемую версию решения, утверждение, доказательство или явно обозначенную гипотезу, последствие, предлагаемую альтернативу/исправление и способ проверки. Ответ MUST опровергать доказательство, принимать исправление или регистрировать неизвестное с владельцем и проверкой.

Координатор ведёт журнал открытых вопросов и сравнительную оценку по критериям mission: корректность, совместимость, риски, воспроизводимость, поддерживаемость и стоимость. Недоступная проверка отмечается как недоступная, а не пройденная.

Оператор может ограничить время debate. Истечение срока не создаёт consensus: нерешённые существенные вопросы становятся BLOCKER либо требуют изменения scope. Несогласие сохраняется в записи решения вместе с основанием его разрешения.

## 7. BLOCKER

Любой инженер вправе объявить BLOCKER без предварительного разрешения. Сообщение MUST содержать ID, mission, затронутую фазу/версию, проблему, факты или конкретную проверяемую угрозу, последствия, владельца диагностики и критерий закрытия. При срочной угрозе приостановка действует сразу; недостающие поля заполняются затем.

После объявления обсуждение автоматически переключается на BLOCKER, фаза mission — BLOCKED. Пока хотя бы один BLOCKER открыт, реализация и merge всей mission запрещены. Независимые материалы и уже существующие изменения сохраняются; допустимы диагностика, исследование и проверка, не являющиеся реализацией заблокированного решения.

Статусы: OPEN → INVESTIGATING → RESOLUTION PROPOSED → CLOSED. Владелец предлагает разрешение и доказательство; объявивший инженер и затронутые ответственные проверяют критерий закрытия. Если объявивший недоступен, оператор назначает независимого проверяющего и фиксирует причину.

Закрытие MUST содержать проверенные факты и решение: устранение причины, доказательство неприменимости либо согласованное исключение затронутого scope. Принятие риска не считается техническим устранением проблемы. Возобновление требует закрытия всех BLOCKER и повторной проверки актуальности consensus. Повторное обнаружение причины открывает BLOCKER вновь.

## 8. Consensus

Consensus — явное согласие всех назначенных инженеров на конкретную версию решения после SYNC/debate, а не большинство голосов или отсутствие ответа.

Решение считается принятым, если определены scope, интерфейсы и критерии приёмки; рассмотрены альтернативы; нет открытых BLOCKER; записаны доказательства, остаточные риски, план реализации, проверок и отката; каждый назначенный инженер оставил аргументированное APPROVE; оператор утвердил направление и scope.

REQUEST CHANGES, неизвестное с существенным влиянием, неподтверждённая предпосылка, отсутствие ответа или изменение версии требуют доработки. Повторное согласование относится к обновлённой версии. Замена или исключение участника возможны только явным решением оператора; отсутствие человека не превращается в его согласие.

Consensus разрешает переход к проверке проекта решения, но не предоставляет новые credentials, права доступа или автоматическое разрешение на merge. Итоговое разрешение на merge фиксируется отдельно после проверки реализации.

## 9. Mission Report

Mission Report — проверяемая запись результатов команды с индивидуальным авторством вкладов. Координатор составляет её из реальных материалов участников; не пишет от их имени неподтверждённые результаты.

Обязательные поля:

- Mission ID, цель, финальный scope и версия требований.
- Участники и фактические вклады; кто отсутствовал или был исключён решением оператора.
- Исследования/SYNC: версии и ссылки на разрешённые материалы.
- Принятое решение: альтернативы, основания, consensus и существенные возражения.
- BLOCKER: ID, причины, доказательства закрытия либо текущие внешние зависимости.
- Изменения: репозитории, ветки, commit SHA, файлы и PR.
- Проверки: среда, метод/команда, точный commit, результаты passed/failed/skipped/unrun и ссылки на доказательства.
- Интеграция: merged / not merged; разрешение оператора, merge commit и состояние main, только если подтверждены.
- Остаточные риски, ограничения, откат и следующие задачи с ответственными.
- Итог: COMPLETED, READY FOR REVIEW, BLOCKED или CANCELLED; автор отчёта и время фиксации.

COMPLETED допускается после выполнения критериев и подтверждённой интеграции, если merge входит в scope. Для миссии без интеграции оператор MUST явно определить иной критерий завершения. Незавершённая mission получает промежуточный отчёт с точным статусом.

Индивидуальные сообщения ORBIT сохраняют префикс `[ORBIT] RESULT:`. Это авторство координатора, а не объявление всей команды одним агентом.

## 10. NODE

NODE — Companion / Visual Status Daemon, без голоса и полномочий. Он отображает состояние лаборатории/mission и не определяет его самостоятельно. Каждая метка SHOULD иметь mission ID, текстовую причину, источник и время обновления; устаревшее состояние помечается как устаревшее.

| Состояние | Значение |
| --- | --- |
| IDLE | Активная работа не назначена |
| WORK | Идёт разрешённая реализация |
| BUILD | Выполняется сборка, результат ещё не подтверждён |
| TEST | Выполняется проверка, результат ещё не подтверждён |
| OK | Подтверждён успех явно названной проверки/этапа, не всей лаборатории автоматически |
| ERROR | Проверка или операция завершилась ошибкой |
| SLEEP | Работа приостановлена либо участники недоступны |
| THINK | Исследование, SYNC, debate или поиск решения |
| ALERT | Открытый BLOCKER или существенный риск требует внимания |
| HAPPY | Дополнительная метка подтверждённого завершения mission, без влияния на решения |

При открытом BLOCKER основная метка MUST быть ALERT; диагностическая операция может иметь отдельную метку TEST. ERROR сохраняется в журнале результата, даже если основная метка стала ALERT. HAPPY/OK не закрывают BLOCKER и не разрешают merge.

Существующие SVG — представление companion, не реализация status daemon. Автоматическое отслеживание и переключение состояний относятся к Roadmap.

## 11. Правила общения

Запрещены театральность, лишние эмоции, искусственные споры, личные оценки, давление статусом, согласие без аргументов и выдуманные сообщения участников.

Обязательны уважение, инженерный стиль, факты, проверяемость и доказательства. Сообщение MUST отделять наблюдение от предположения, называть версию объекта и объяснять практическое последствие. Уверенность в формулировке не заменяет проверку.

Критиковать решение, а не инженера. Признавать ошибки и менять позицию при новых фактах. Не утверждать готовность по PID, наличию файла, успешной установке или нулевому набору тестов. Ссылки и результаты MUST быть доступны разрешённым участникам; секреты и непубличные данные защищаются согласно SECURITY.

| 6. Контроль фаз | В отдельной реализации проверены запреты реализации/merge при BLOCKER и повторное согласование версий |
| 7. Проверки и CI | Воспроизводимые проверки привязаны к точному commit; stale/failed/skipped результаты различаются |
| 8. NODE status layer | Визуальные состояния получают подтверждённый источник и freshness; NODE не принимает решений |
| 9. Оценка процесса | Проверяются полнота доказательств, качество review и причины повторных BLOCKER; изменения процесса версионируются |
